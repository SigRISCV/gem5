# 阶段 2 设计计划：增加 ID 语义与扩展基础算术

## 1. 阶段 2 的目标

阶段 2 的目标是在阶段 1 已经建立的 CSR 骨架和 `DEBUG` 调试通路之上，第一次把“ID 是 GPR/PC 的伴随状态”这个核心语义真正接入 gem5 的功能执行路径。

这一阶段的交付重点有三个：

1. 打通 `gprid0-31`、`pcid`、`IDCSR.use/puse` 的功能语义。
2. 实现 `SETDUMMYID` 和 `SETRAWID` 两条基础扩展算术指令。
3. 让一小组普通 RISC-V 指令按设计规则传播或清空 ID，为阶段 3 的 `SETNEWID` 和后续 `LS/SS` 做好基础。

这里的“打通”特指功能模型闭环，而不是时序流水线闭环。也就是说，本阶段的正确性目标是：

1. `AtomicSimpleCPU` / `TimingSimpleCPU` 上语义正确。
2. CSR 与普通 GPR 写回之间的 ID 关联关系正确。
3. `DEBUG` 可以直接观察到每一步 ID 变化。

本阶段不要求：

1. `MinorCPU` 具备流水线级的 ID 旁带与回滚机制。
2. `SETNEWID`、`LS/SS`、`LS_MAP`、`SS_ID`、`SWITCHS` 已实现。
3. 对普通指令时序进行任何建模。

## 2. 为什么阶段 2 要这样切

阶段 2 是这套扩展第一次把“CSR 可见状态”推进到“普通指令执行结果”，所以必须控制范围，避免同时引入过多变量。

这样切分有四个直接好处：

1. `SETDUMMYID/SETRAWID` 都是 `ADDI` 的近邻语义，最适合作为第一批真正落地的扩展指令。
2. `add/sub/addi/auipc/jal/jalr` 的 ID 传播规则足够覆盖“数据流”和“控制流”两种核心路径，但还不涉及加解密和访存。
3. `use=0` 时的降级规则在这一阶段就能被明确验证，后续每个阶段都能复用这套判断基线。
4. 如果这一阶段先在功能线上验证清楚 ID 传播规则，阶段 4 再把同样规则搬到 `MinorCPU` 时，问题会从“语义不清”收缩成“流水实现是否一致”。

## 3. 本阶段的边界

### 3.1 本阶段要完成的内容

1. 为 `PCID` 增加统一只读 helper，并把它纳入常用 debug 观察路径。
2. 为 `IDCSR` 增加最小字段 helper，至少能稳定判断 `use` 与 `puse`。
3. 实现 `SETDUMMYID` 与 `SETRAWID` 的 decode、反汇编和 execute 语义。
4. 为普通指令补入 ID 更新语义：
   1. `add/sub/addi` 传递 `rs1` 的 ID 到 `rd`。
   2. `auipc/jal/jalr` 传递 `pcid` 到 `rd`。
   3. 其他写整数寄存器的普通指令，在需要纳入阶段 2 覆盖的范围内默认清空 `rd` 的 ID。
5. 明确并实现 `use=0` 时的退化规则，特别是 U 态下“任何普通指令不能影响 ID”。
6. 补齐阶段 2 的 baremetal 汇编测试与最小回归脚本。

### 3.2 本阶段明确不做的内容

1. 不实现 `SETNEWID`。
2. 不实现 `LS/SS/LS_MAP/SS_ID`。
3. 不实现 `SWITCHS`。
4. 不改 `cpu/minor/*` 的动态指令、scoreboard、pipe data 或 flush 逻辑。
5. 不在这一阶段引入 `use/puse/idgen/encmap/exitraw` 的 shadow state。
6. 不尝试兼容 `O3CPU`。

## 4. 阶段 2 的核心设计决策

### 4.1 `gprid/pcid` 仍然先作为架构态实现

本阶段仍然坚持阶段 1 的策略：`gprid0-31` 和 `pcid` 在 gem5 中先表现为 ISA 层可见的架构状态，而不是新的独立重命名资源。

因此阶段 2 的实现原则是：

1. 每次普通指令写 `rd` 时，同时由 ISA helper 决定是否更新 `rd` 对应的 `gprid`。
2. 每次控制流相关指令需要“从 PC 产生一个值”时，通过 `pcid` helper 提取当前 PC 对应的 ID。
3. 所有这些更新都只要求在功能模型正确，不追求时序流水线内部旁带传播。

这和阶段 4 的关系是：阶段 2 先定义“提交后的最终状态是什么”，阶段 4 再决定“流水中怎么携带这些状态”。

### 4.2 `use` 是阶段 2 的总开关，`puse` 只读不驱动行为

按整体规划，真正会主动修改 `puse` 的是 `SWITCHS`，那是阶段 7 之后的事情。因此阶段 2 对 `IDCSR` 的要求只做到以下两点：

1. 通过 helper 稳定读取 `use` 位。
2. `DEBUG` 输出时继续按 `puse/use/idgen` 展开，便于 bring-up。

行为上，本阶段只有 `use` 参与判定：

1. 在 U 态，`use=0` 时，任何普通指令都不能改变任何 GPRID，也不能改变 `PCID`。
2. 在 U 态，`use=1` 时，普通指令按阶段 2 的传播/清空规则更新 GPRID。
3. 在 S/M 态，本阶段先按“扩展语义始终生效”处理，不额外要求 `use=1` 才允许 ID 更新。

这样切分的原因是：架构文档中“U 态 + use 开关”的约束是最明确、也是最需要尽早锁定的；而 `puse` 的动态联动还要等 `SWITCHS` 落地。

### 4.3 `x0` 的值仍保持 0，但其 GPRID 也必须视为不可保留

RISC-V 的 `x0` 永远不会真正写入新值，因此阶段 2 建议把“对 `rd=x0` 的 ID 更新”统一降为 no-op。

也就是说：

1. `add x0, ...`、`setdummyid x0, ...`、`jal x0, ...` 都不修改 `GPRID0`。
2. `csrw gprid0, ...` 作为显式 CSR 访问仍然允许，因为它是软件直接操作扩展状态。

这样做能避免后续在普通指令模板里出现“值没写进去但 ID 被写脏”的不一致。

### 4.4 阶段 2 不追求“一次性覆盖所有整数指令”的 ID 清空

“其他写 GPR 的指令清空目标 ID”这条总规则最终是要全面落地的，但在阶段 2 不建议一次性把所有整数指令模板都改完。更稳妥的策略是：

1. 第一批必须覆盖：`add/sub/addi/auipc/jal/jalr`、`SETDUMMYID`、`SETRAWID`。
2. 第二批必须覆盖：常见会写整数寄存器、且最容易在测试里与上面指令串起来的指令，例如 `lui`、逻辑立即数、位移立即数、比较类写回。
3. 对未在本阶段显式覆盖的整数写回指令，在文档里先标记为“阶段 2 可暂不保证”，避免开发时为了追求完整性而大面积扰动现有模板。

换句话说，阶段 2 的目标是建立一条稳定的实现模式，而不是把全部清空规则一口气铺到整个 RISC-V 整数 ISA。

### 4.5 优先评估“重写 RD 写回接口默认清空 GPRID”

这一点需要按实现可行性重新评估。我认为它值得作为阶段 2 的优先方案，但不能在文档里先验假设一定能做成。

推荐优先尝试的方案是：

1. 在整数寄存器 `rd` 的公共写回路径附近增加一个“默认清空 `rd.gprid`”的统一钩子。
2. 对绝大多数普通整数写回指令，沿用这条默认路径，因此天然获得“写 `rd` 就清空 GPRID”的行为。
3. 对少数需要保留或重写 ID 的特殊指令，改用单独的自定义写回路径，而不是默认清空路径。

这一组特殊指令主要包括：

1. `add/sub/addi`，它们要传播 `rs1` 的 GPRID。
2. `auipc/jal/jalr`，它们要传播 `PCID`。
3. `SETDUMMYID/SETRAWID`，它们要写入常量 ID。
4. 阶段 3 的 `SETNEWID`，它要写入 `IDCSR.idgen`。

这个方案的优点是：

1. 普通整数写回的默认清空语义可以集中落在一个地方。
2. 不容易遗漏零散整数指令。
3. 后续阶段继续增加特殊写回语义时，代码结构会更整齐。

但它成立的前提是：gem5 当前 RISC-V `.isa` 生成代码中，整数 `rd` 写回必须存在一个足够稳定、足够集中的公共落点，可以安全区分“默认清空”和“特殊传播/特殊写入”。

因此阶段 2 的实施策略应该分成两层：

1. 首选方案：如果存在清晰的整数 `rd` 公共写回接口，就在这里实现默认清空。
2. 降级方案：如果写回路径分散或生成代码难以安全统一插桩，就退回到“只改关键指令模板”的方案。

### 4.6 如果无法统一改写写回接口，就只覆盖关键模板

如果前面的统一写回方案做不到，阶段 2 仍然可以保持简洁，做法是：

1. 把 `add/sub/addi/auipc/jal/jalr/SETDUMMYID/SETRAWID` 作为必须覆盖集。
2. 再补少量最常见、最适合暴露“应清空未清空”问题的普通立即数类写回指令。
3. 暂时不追求一次性覆盖全部整数写回指令。

在这个降级方案里，建议优先补齐的清空类指令仍然是：

1. `lui`
2. `andi/ori/xori`
3. `slli/srli/srai`
4. `slt/sltu/slti/sltiu`

这样可以用较小的改动量把阶段 2 的传播、清空、退化三类行为都测出来，同时避免在 `.isa` 大范围散改。

## 5. 详细语义建议

### 5.1 `SETDUMMYID`

建议语义：

1. 数据结果与 `ADDI` 相同，`rd = rs1 + sext(imm)`。
2. 当扩展语义生效时，`rd` 对应的 `GPRID` 被写为 1。
3. 当扩展语义不生效时，其行为完全退化为 `ADDI`，不得改变 `rd` 的 GPRID。
4. `rd=x0` 时不更新 `GPRID0`。

这里“扩展语义生效”的最低要求是：

1. U 态下 `use=1`。
2. 非 U 态下默认生效。

### 5.2 `SETRAWID`

建议语义：

1. 数据结果与 `ADDI` 相同，`rd = rs1 + sext(imm)`。
2. 当扩展语义生效时，`rd` 对应的 `GPRID` 被写为 0。
3. 当扩展语义不生效时，其行为完全退化为 `ADDI`，不得改变 `rd` 的 GPRID。
4. `rd=x0` 时不更新 `GPRID0`。

它和 `SETDUMMYID` 的模板基本一致，只是写入的目标 ID 常量不同，因此非常适合作为同一组 custom I-type 模板的两个实例。

### 5.3 `add/sub/addi`

建议语义：

1. 数据结果沿用 gem5 现有整数算术语义。
2. 当扩展语义生效时，`rd` 的 GPRID 取 `rs1` 的 GPRID。
3. 当扩展语义不生效时，不得改变 `rd` 的 GPRID。
4. `rd=x0` 时不更新 `GPRID0`。

这里明确选择“只传播 `rs1` 的 ID”，不尝试融合 `rs1/rs2`，因为这正是架构文档已经给出的规则。

### 5.4 `auipc/jal/jalr`

建议语义：

1. 数据结果沿用标准 RISC-V 语义。
2. 当扩展语义生效时，`rd` 的 GPRID 取当前 `PCID`。
3. 当扩展语义不生效时，不得改变 `rd` 的 GPRID。
4. `rd=x0` 时不更新 `GPRID0`。

阶段 2 暂不要求这些指令修改 `PCID` 本身，只要求它们在“生成返回地址或 PC 相对结果”时消耗当前 `PCID`。

### 5.5 其他写 GPR 指令的清空策略

建议把阶段 2 的清空规则表述为：

1. 在 U 态且 `use=1` 时，凡是被阶段 2 纳入覆盖范围、且会写整数寄存器的普通指令，如果不属于“传播 `rs1` 的算术类”或“传播 `pcid` 的控制流类”，则应清空 `rd` 的 GPRID。
2. 在 U 态且 `use=0` 时，这些指令一律不得改变 `rd` 的 GPRID。
3. 非 U 态下，本阶段先不强求对所有普通整数写回指令补齐清空规则；如果某些路径实现成本过高，可以在阶段 2 文档里先限定覆盖范围。

如果采用“关键模板覆盖”的降级方案，阶段 2 建议优先补齐的清空类指令有：

1. `lui`
2. `andi/ori/xori`
3. `slli/srli/srai`
4. `slt/sltu/slti/sltiu`

这组指令足以支撑大部分最小 baremetal 测试，也能很好地暴露“应清空但未清空”的 bug。

## 6. 模块级实现计划

### 6.1 `arch/riscv/isa.hh`

职责：声明阶段 2 需要的 ID 语义 helper。

本阶段计划改动：

1. 增加 `readPcid()`。
2. 增加 `readIdcsrUse()` / `readIdcsrPuse()` 或等价字段 helper。
3. 增加“当前指令是否应触发 ID 语义”的判定 helper。
4. 如果统一写回方案可行，增加整数 `rd` 默认写回与自定义写回的区分接口。
5. 如果统一写回方案不可行，则增加 `propagateRs1IdToRd()`、`propagatePcidToRd()`、`clearRdId()`、`writeRdIdImmediate()` 这类显式 helper。

设计注意点：

1. helper 尽量接受 `ExecContext *xc` 和架构寄存器号，避免和某一种 CPU 实现绑死。
2. helper 内部要统一处理 `rd=x0` 的 no-op 规则。
3. `PCID` 的写入不需要新增 helper，因为显式 `csrw pcid, ...` 在阶段 1 已经具备。
4. 阶段 3 的 `SETNEWID` 要能复用阶段 2 建立的特殊写回接口。

### 6.2 `arch/riscv/isa.cc`

职责：实现阶段 2 的核心 ID 语义后端。

本阶段计划改动：

1. 补齐 `PCID` 的只读 helper。
2. 补齐 `IDCSR.use/puse` 的字段读取 helper。
3. 实现“是否应用 ID 语义”的统一判定。
4. 优先评估并实现整数 `rd` 默认写回时的 GPRID 清空逻辑。
5. 为特殊指令实现绕过默认清空、改为传播或常量写入 GPRID 的路径。
6. 视需要增强 `DEBUG imm=0/3/4` 的输出，使 bring-up 时更容易看出 `PCID/use` 状态。

设计注意点：

1. `IDCSR` 字段建议统一通过 bit helper 读取，不在各处手写 `bits(..., 30, 30)`。
2. 如果统一写回方案落在生成代码公共路径上，要严格限定它只影响整数 `rd` 写回，不误伤 CSR、浮点或其他非目标路径。
3. 阶段 2 不建议把“清空所有 GPRID”之类的批量操作放进 ISA 层，避免过早为 `SWITCHS` 设计接口。

### 6.3 `arch/riscv/isa/decoder.isa`

职责：扩展 custom opcode 的 decode。

本阶段计划改动：

1. 在 `opcode=0b1011011` 下接入 `func3=0b010` 的 `SETDUMMYID`。
2. 在 `opcode=0b1011011` 下接入 `func3=0b110` 的 `SETRAWID`。
3. 保持已存在的 `DEBUG` 路径不变。

设计注意点：

1. `func3=0b011` 未来要留给 `SETNEWID`，不要在阶段 2 抢占。
2. custom I-type 的 decode 组织方式要能和后续 `LS/LS_MAP` 共存。

### 6.4 `arch/riscv/isa/formats/*.isa` 与相关指令模板

职责：把阶段 2 语义挂进具体指令 execute 模板。

本阶段计划改动：

1. 为 `SETDUMMYID/SETRAWID` 增加 custom I-type 执行模板。
2. 如果统一写回方案可行，在 `add/sub/addi` 的 execute 模板里切换到“传播 `rs1` 的自定义写回”。
3. 如果统一写回方案可行，在 `auipc/jal/jalr` 的 execute 模板里切换到“传播 `pcid` 的自定义写回”。
4. 如果统一写回方案不可行，则在这些模板后追加显式 helper 调用。
5. 在降级方案下，为选定的“应清空 ID”整数写回指令追加清空 helper 调用。

设计注意点：

1. 指令模板里不要重复写权限和 `use` 判断，这些都收敛到 ISA helper。
2. 如果某些指令共享同一个生成模板，优先在共享模板中加钩子，而不是复制多份逻辑。
3. 阶段 2 不要在 `.isa` 模板中直接读写 CSR 编号，全部走 helper。
4. 如果统一写回方案确实能落在模板公共层，那么优先用公共层方案，不要再额外给普通清空类指令逐条散改。

### 6.5 `cpu/simple/*`

职责：确认 `SimpleCPU` 执行路径无需额外改造即可承载阶段 2 helper。

本阶段预期：

1. 大概率不需要单独修改 `cpu/simple/*` 的控制逻辑。
2. 如果某些 execute 路径拿不到需要的 `ExecContext` 或寄存器编号，再做最小接口补丁。

设计注意点：

1. 阶段 2 的首选策略是把变化限制在 `arch/riscv/*`。
2. 只有在 helper 接口被现有执行框架卡住时，才去补 `cpu/simple/*`。

## 7. 测试计划

### 7.1 测试目标

阶段 2 的测试要验证三类问题：

1. 扩展指令本身是否正确。
2. 普通指令的 ID 传播和清空是否正确。
3. `use=0` 的降级路径是否真的“不影响 ID”。

### 7.2 建议测试目录

参考当前 `benchmark/simple-sigriscv-test/gem5_test/tests/` 只有少量阶段级测试文件的组织方式，阶段 2 不建议拆成很多小文件。

建议直接新增两个主测试文件：

1. `benchmark/simple-sigriscv-test/gem5_test/tests/stage2_u_mode.S`
2. `benchmark/simple-sigriscv-test/gem5_test/tests/stage2_s_mode.S`

如果后续发现单文件过长，也建议最多再拆成 3 个文件，而不是把每个子行为都单独拆成一个测试。

### 7.3 关键测试点

#### `stage2_u_mode.S`

建议把 U 态相关行为集中在一个文件里，按子段顺序依次验证：

1. `use=1` 时 `SETDUMMYID/SETRAWID` 的数值与 GPRID 结果。
2. `add/sub/addi` 对 `rs1` GPRID 的传播。
3. `auipc/jal/jalr` 对 `PCID` 的传播。
4. 被阶段 2 纳入范围的普通写回指令对 GPRID 的清空。
5. 把 `use` 清零后再次执行上述关键指令，确认全部退化为“数值正常但 ID 不变”。

这样写的好处是：

1. 一个文件内就能覆盖阶段 2 最核心的 U 态语义。
2. `DEBUG` 和失败码可以沿着同一条执行流逐段定位。
3. 不需要为每个子语义维护独立启动和收尾逻辑。

#### `stage2_s_mode.S`

建议把 S 态相关行为集中在另一个文件里，重点验证：

1. 显式 `csrw gprid*` 和 `csrw pcid` 后，普通传播语义在 S 态也能工作。
2. `SETDUMMYID/SETRAWID` 在 S 态按扩展语义生效，不受 `use=0` 限制。
3. `add/sub/addi/auipc/jal/jalr` 的传播行为在 S 态和设计约束一致。
4. 如果采用统一写回默认清空方案，验证普通整数写回在 S 态下的清空行为是否符合当前阶段定义。

S 态测试的价值主要是把“U 态受 `use` 约束”和“非 U 态按扩展语义工作”明确区分开。

### 7.4 调试与观测手段

阶段 2 测试建议继续依赖：

1. `DEBUG imm=0` 做全量状态快照。
2. `DEBUG imm=3` 直接查看某个 GPR 及其 GPRID。
3. `DEBUG imm=4` 查看 `PCID`、`IDCSR` 等 CSR。

但在大测试文件组织下，建议只保留少量关键节点的 debug：

1. 进入核心子段前一次。
2. 某个传播或清空断言失败前一次。
3. 最终 pass 前按需一次。

这样既保留可观测性，也不会让日志被大量重复输出淹没。

## 8. 风险与应对

### 8.1 最大风险：整数 `rd` 写回公共落点不够集中

风险：

1. 如果 gem5 的整数 `rd` 写回没有足够清晰的公共落点，那么“默认清空 GPRID”的统一方案可能难以安全落地。
2. 一旦退回到零散模板修改，就容易出现“某条指令保留了旧 ID”的遗漏。

应对：

1. 开发初期先验证统一写回方案是否可行，再决定是否切换到降级方案。
2. 如果退回到关键模板覆盖，就先限定范围。
3. 每补一组指令，就配一组最小汇编回归。
4. 文档里明确哪些类别已经纳入，哪些留到后续阶段。

### 8.2 风险：`use=0` 的降级语义和 S/U 态边界混淆

风险：

1. 如果判断逻辑散在模板里，后续很容易出现某些路径在 U 态仍错误更新 ID。

应对：

1. 所有“是否执行 ID 语义”的判定统一收敛到 helper。
2. 用单独测试专门覆盖 U 态 + `use=0`。

### 8.3 风险：`PCID` 传播点选错

风险：

1. `auipc`、`jal`、`jalr` 的“取哪个时刻的 PC”本身就容易写错。
2. 如果把值计算和 ID 传播绑得过紧，后续调试会比较难拆分。

应对：

1. 数据结果继续完全沿用 gem5 原有实现。
2. ID 传播只在结果已经确定后附加执行。
3. 用 `csrw pcid, const` + 单条指令观测的测试把 bug 面缩小。

## 9. 预估改动范围

如果按上面的切分推进，阶段 2 预计会修改 4 到 7 个模块，主要集中在 `arch/riscv`：

1. `repo/gem5/src/arch/riscv/isa.hh`
2. `repo/gem5/src/arch/riscv/isa.cc`
3. `repo/gem5/src/arch/riscv/isa/decoder.isa`
4. `repo/gem5/src/arch/riscv/isa/formats/*` 或相关指令模板
5. `benchmark/simple-sigriscv-test/gem5_test/tests/stage2_u_mode.S`
6. `benchmark/simple-sigriscv-test/gem5_test/tests/stage2_s_mode.S`
7. 如有需要，少量更新测试 `Makefile` 或 README

从实现难度看，本阶段整体属于“中等偏上”，难点不在单条指令本身，而在于：

1. 判断 gem5 的整数 `rd` 写回路径是否足够集中，值得做统一默认清空。
2. 如果做不到统一清空，要控制好覆盖范围，避免模板大面积散改。
3. 尽早把 `use=0` 降级行为锁死。

## 10. 验收标准

阶段 2 完成的判据建议为：

1. `SETDUMMYID` 和 `SETRAWID` 能正确 decode、反汇编和执行。
2. `add/sub/addi` 能按 `rs1` 传播 GPRID。
3. `auipc/jal/jalr` 能按 `PCID` 传播到 `rd`。
4. 普通整数写回的 GPRID 清空，要么已经通过统一写回接口默认生效，要么至少对阶段 2 选定的关键立即数类指令生效。
5. 在 U 态且 `use=0` 时，阶段 2 覆盖的所有相关指令都不会改变 ID。
6. baremetal 阶段 2 用例以少量大文件形式稳定构建，并可通过 `DEBUG` 直接观测结果。

## 11. 与阶段 3 的衔接点

阶段 2 完成后，阶段 3 将可以在不改变整体结构的前提下直接推进：

1. 复用阶段 2 的 helper 体系，为 `IDCSR.idgen` 增加字段级读写。
2. 复用阶段 2 的特殊写回路径实现 `SETNEWID`。
3. 复用已经建立的 stage2 大测试骨架，把 `SETNEWID/idgen` 子段并入对应的 U/S 态测试，或在确有必要时再单独拆文件。

换句话说，阶段 2 的目标不是把 ID 扩展“做大”，而是把后续所有阶段都会依赖的“ID 功能语义底座”做稳。
