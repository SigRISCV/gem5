# 阶段 0 详细评估与实施计划

## 1. 阶段 0 的目标

阶段 0 不进入 gem5 主功能实现，而是完成后续开发的基线整理工作。它的目标不是“实现扩展指令”，而是把后续阶段必须稳定的三类基础设施先固定下来：

1. 设计基线：把扩展的编码、CSR 分配、行为边界、降级规则、回滚边界写清楚。
2. 目录基线：把设计文档、测试目录、汇编测试约定固定下来。
3. 验证基线：提供一个可复用的 baremetal 汇编测试骨架，后续每个阶段都能直接往里加新用例。

## 2. 为什么阶段 0 很重要

从这个项目的特点看，阶段 0 的价值很高，原因有四个：

1. 这个扩展同时跨越 ISA、CSR、功能模型、时序模型和流水线 shadow state，如果一开始没有文档和测试约定，后面很容易在“语义变更”和“实现 bug”之间混淆。
2. 你后续要走 `SimpleCPU` 和 `MinorCPU` 双线开发，必须先定义二者共享的测试输入和预期输出格式，否则同一个 bug 会被写成两套测试。
3. 这套扩展有大量“use=0 时退化为原始指令”的规则，阶段 0 就应该把退化语义作为测试约定的一部分，而不是等到后面再补。
4. 你已经有最小 baremetal 环境，因此最合适的策略不是马上写 C 测试，而是先把汇编测试基础设施做好，确保每条指令都能被最小化隔离验证。

## 3. 阶段 0 的边界

### 3.1 本阶段要完成的内容

1. 统一文档位置到 `repo/gem5/design-doc/`。
2. 细化阶段 0 的设计评估、交付物和验收标准。
3. 给 `gem5_test` 增加可扩展的汇编测试目录结构。
4. 给 `gem5_test/Makefile` 增加“按测试名构建”的能力。
5. 建立通用汇编测试宏，统一 pass/fail/signature 的表达方式。
6. 提供至少一个 smoke test，验证测试框架能正确编译和链接。

### 3.2 本阶段明确不做的内容

1. 不修改 `repo/gem5/src/arch/riscv/*`。
2. 不引入新的 CSR。
3. 不实现 `DEBUG`、`SET*ID`、`LS/SS`、`SWITCHS`。
4. 不进入 `MinorCPU` 或 `SimpleCPU` 的执行逻辑修改。
5. 不要求自动判定 pass/fail，只要求产出统一的状态写回约定。

## 4. 阶段 0 的关键决策

### 4.1 文档组织决策

建议后续文档采用三层结构：

1. `gem5-design.md`：总计划，总体分阶段安排。
2. `arch-design.md`：原始需求与架构设想，作为需求归档。
3. `stageN-*.md`：每个阶段的细化设计、决策与验收标准。

这样做的好处是总计划不需要频繁改动，而阶段文档可以独立迭代。

### 4.2 汇编测试组织决策

建议测试目录采用下面的组织：

1. `tests/common/`：通用宏、公共头文件、共享约定。
2. `tests/stage0/`：框架 smoke test。
3. `tests/stage1/` 及后续目录：每阶段新增用例。

这样能避免所有测试平铺在根目录，也方便后面切换到 C 测试时继续复用。

### 4.3 测试结果表达决策

在 `DEBUG` 指令还没有实现之前，本项目的 baremetal 汇编测试建议采用“内存状态 + 自旋结束”的约定：

1. 每个测试维护一个 `test_status` 符号。
2. `test_status = 1` 表示通过。
3. `test_status = 非 1` 表示失败码。
4. 程序末尾进入固定自旋标签，便于后面在 trace、GDB 或内存检查里定位。

这个约定的优点是简单、稳定，而且未来实现 `DEBUG` 后也不需要推翻，只需要补充更友好的输出方式。

## 5. 阶段 0 的风险评估

### 5.1 低风险项

1. 文档整理。
2. 目录结构调整。
3. 汇编宏封装。
4. `Makefile` 增强。

### 5.2 中风险项

1. 工具链与 include 路径是否稳定。
2. 裸机链接脚本是否适用于后续更多测试。
3. 当前 baremetal 配置是否方便后续批量运行测试。

### 5.3 风险应对

1. 不替换已有 `init` 流程，只在其上增加新测试入口，避免破坏现有使用方式。
2. 通用宏只依赖标准 RISC-V 汇编，不绑定任何尚未实现的扩展指令。
3. 测试骨架只做最小假设，后续如需切 C 测试，再在 `Makefile` 上增量扩展。

## 6. 阶段 0 的详细开发步骤

### 步骤 1：整理阶段文档

输出：
1. `stage0-design.md`。
2. 在总计划文档中登记阶段 0 的落地产物位置。

验收：
1. 阶段 0 目标、边界、交付物、验收标准明确。
2. 后续阶段能直接引用该文档，不需要重新解释测试约定。

### 步骤 2：建立汇编测试目录结构

输出：
1. `tests/common/`。
2. `tests/stage0/`。
3. `README.md` 说明测试约定。

验收：
1. 目录结构稳定。
2. 新增测试不需要继续修改目录规划。

### 步骤 3：定义公共测试宏

输出：
1. `test_setup`。
2. `test_pass`。
3. `test_fail code`。
4. `test_done`。

验收：
1. 后续单条指令测试只需要专注指令本身，不需要重复写收尾逻辑。
2. 失败码可区分不同断言点。

### 步骤 4：扩展 Makefile

输出：
1. 保留 `init` 目标。
2. 新增按 `TEST=stage0/xxx` 构建的目标。
3. 自动把产物放到 `build/` 目录下。

验收：
1. 原有 `make init` 仍可用。
2. `make test-elf TEST=stage0/smoke_arith` 可单独构建新测试。

### 步骤 5：写阶段 0 smoke test

输出：
1. 一个最小汇编算术测试。
2. 用通用宏记录通过或失败。

验收：
1. 能编译和链接。
2. 能作为后续所有测试的模板。

### 步骤 6：本地验证

输出：
1. 至少执行一次 smoke test 编译。
2. 如环境允许，执行一次 baremetal 运行。

验收：
1. 工具链路径正确。
2. 产物布局符合预期。

## 7. 阶段 0 的交付物

本阶段建议产出以下文件：

1. `repo/gem5/design-doc/stage0-design.md`
2. `benchmark/simple-sigriscv-test/gem5_test/README.md`
3. `benchmark/simple-sigriscv-test/gem5_test/tests/common/test_macros.S`
4. `benchmark/simple-sigriscv-test/gem5_test/tests/stage0/smoke_arith.S`
5. 更新后的 `benchmark/simple-sigriscv-test/gem5_test/Makefile`

## 8. 阶段 0 的验收标准

阶段 0 完成的判据建议为：

1. 文档中明确阶段 1 开始前不再反复讨论测试组织方式。
2. 新增汇编测试可通过统一入口构建。
3. smoke test 可成功生成 `.elf/.bin/.dump`。
4. 原有 `init` 目标不被破坏。
5. 后续阶段新增用例时，只需要新增 `.S` 文件和少量 `Makefile` 参数，不需要再重构框架。

## 9. 阶段 1 的衔接点

阶段 0 完成后，阶段 1 可以直接开始：

1. 在 `arch/riscv/regs/misc.hh` 中加入新 CSR。
2. 在 `arch/riscv/isa/decoder.isa` 中加入 `DEBUG`。
3. 在 `tests/stage1/` 中新增 `debug_imm0.S`、`debug_imm1.S` 等汇编用例。

也就是说，阶段 0 的目标就是让阶段 1 不再被“文档没定、测试没框架、路径不统一”这些非核心问题卡住。
